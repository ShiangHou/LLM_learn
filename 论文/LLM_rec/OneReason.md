# OneReason

## 推荐算法基础

生成式推荐类似于大模型中的next token predict，给定一段的序列，然后预测下一个用户的行为

所以一个很显然的想到的是，我们需要把产品、商品或者要推荐的东西都变成token的形式

比如

帐篷 = item_98731

这个就可以叫做itemID

但是这里有一些的区别

1:推荐没有唯一的答案

这个很好理解，因为用户的下一个行为受到的影响的因素有很多，
从模型输出的角度来看的话，相当于，推荐是在一大组物品的空间里面去找到**一组**可能的答案

2:用户意图不可察觉

我们只有用户的一大段的行为序列，所以这个其实很依赖推理反馈，即从行动反推出用户要干嘛

3:协同信号

这个的意思是，如果行动A->行动B，如果这个组合在线上有90%都会这么做，那么这个用户很有可能也会这么做，即使这两个行动没啥关联，在模型看来，这个学不会这种线上的规律

### 推荐算法演进
#### 传统推荐算法
典型方法包括矩阵分解、SASRec、HSTU 等。

以 SASRec 为例，可以把它理解为：

[item_1, item_7, item_15, item_28]
              ↓ Transformer
          预测 item_42

它和语言模型很像，只不过词表不是中文词，而是平台上的 item ID。

优点是：

能从真实用户行为中学习协同关系；
能建模用户行为的先后顺序；
推理速度快；
很适合大规模线上系统。

但它有两个明显问题。

问题一：ID 本身没有语义

对于模型来说：

item_12345
item_12346

只是两个完全不同的 embedding。

模型不知道：

一个是帐篷；
一个是露营灯；
它们都属于户外装备；
它们之间存在场景关系。

这些关系只能依靠大量交互数据“背出来”。

问题二：冷启动

如果一个新商品从未出现在训练数据里，它的 ID 没有被充分训练，模型几乎不知道该如何推荐它。

报告中的跨域测试里，传统 item ID 目标中约有 33.69% 是训练阶段未出现过的 ID，因此 ID 模型受到严重冷启动影响。

#### 生成式推荐

不再为每个物品设置一个完全独立的 ID，而是把一个物品表示成若干个可组合的离散 token。

这个token就是SID

比如<|video_begin|><a_5028><b_6733><c_2559>

就是视屏、粗颗粒度、细颗粒度、细细颗粒度

这个ID不是人工定义的，是通过向量语义训练出来的

### CoT增强训练
在One系列的oneRec和openOneRec中，试图想要使用LLM的推理能力去增强
他们加入了：

item token 和文本交错的数据；
通用数学、代码、逻辑推理数据；
Thinking / Non-thinking 两种输出方式；
推荐领域的 SFT 和 RL。

模型确实学会了：

<think>
用户最近关注露营装备，并且从泛泛浏览逐渐转向具体商品搜索，
说明需求已经进入购买决策阶段……
</think>
<|prod_begin|><a_x><b_y><c_z>

但结果出现了一个意外现象：

这段推理看起来很合理，最终推荐却没有比直接输出 item token 更准确。

这就是 OneReason 的直接起点。

总结一下，作者的目的就是，利用LLM的Cot能力去增强在推荐场景的能力

作者总结了一下，主要有两点的原因，

第一个就是模型并没有真正理解 itemic token

即给一个itemic token，模型就只是记得这个token一般什么时候出现，一般跟在哪些里面，但是其实本质上模型就不知道这些token背后究竟是什么意思，表达的是什么产品，导致输出的不好

第二个是推理本身的问题

即，模型在推荐场景的Cot是有问题的，不能瞎jb推理，而是要按照

用户看了几个视频，不代表一定会购买某商品。

因此，推荐 CoT 应该完成的是：

从长历史中选择相关行为
       ↓
压缩成若干潜在兴趣
       ↓
分析兴趣的时间演化
       ↓
比较多个下一步可能性
       ↓
选择最可能的方向

这样去做

另一个是RL，在四个任务上，，如果同时训练的话，
短视频；
商品；
广告；
直播。

共同更新一个模型，可能会导致冲突，就是梯度不一样，

就是在单领域中，单领域 RL 中，Thinking 能稳定超过 Non-thinking；
混合多领域 RL 中，这个优势会减弱或消失。
