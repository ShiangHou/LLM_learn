# MOE 混合专家

所谓的混合专家，只是说替换了原来的的FFN层

在模型框架方面，我们的一个block是一层MLP然后解了一个FFN，这里就换成了一个MOE框架

![image-20260529002935794](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260529002935794.png)



这里有几个思想，首先是为什么要这么做

一个是，其实并不是所有的token都需要经过全部的层，它可以只经过一部分

另一个是，如果我每次可以选择经过一部分的话，那么整体的我就可以做的很宽，即一下子在MOE层堆很多的参数，但是我只选择一部分

（这个其实没有完全考量，原来的是，比如1万个token走的都是同一个链接，现在1万个token，可能2000个走一个，2000个走另一个，这样子，即不同的token走不同的ffn，不同的语义会激活不同的ffn，这样下来，如果还想靠简单的一个大FFN得到效果，就要堆的很大，而现在就可以直接每一个小部分只激活一点就行了）



所以说，这里有三个概念**Total parameters**：模型总参数量，包括所有专家。**Activated parameters**：每个 token 实际激活的参数量。我们常见的什么Qwen3 A3B 这样的A3B就是激活参数是3B。**FLOPs**：每个 token 实际计算量，这个我们上一章有讲过

MOE，就是会显著增加模型总参数量，但是activate和FLOPs并不会显著的增加，非常的好

# MOE的问题

## 小规模没有优势

MOE在小规模的单卡上其实没有优势 ，

因为 MoE 需要：

- 将专家分布到不同设备；
- 将 token 发送给对应专家；
- 在专家计算完成后再聚合输出；
- 处理 expert load imbalance；
- 处理 all-to-all communication。

对于一个dense模型，虽然参数多，但是训练数据较为规则

对于Moe模型来说，虽然每个token计算少，但是数据不是规则的

# MOE的设计点

总结一个下三个点，

1：token怎么选择专家

2：每个专家的size怎么设置

3：训练的时候怎么让专家更高效



## Routing

这个就是说，怎么选专家，目前有几种方法

 ![image-20260530104839837](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530104839837.png)

图比较形象，

目前用的最多的就是 Token chooses expert，就就是一个token进来后，从所有的专家中选择一个

Token t
→ router 计算 expert scores
→ 选择 top-k experts
→ 送入这些 experts



Expert chooses token

另一种方式是专家选择 token。

也就是说，每个专家根据某种打分，从 batch 中选择自己要处理的 token。

这样做的理由是，在理论上，可以更好地控制专家负载，因为每个专家可以限制自己接收多少 token。

但问题是：

- 实现复杂；
- token 可能被多个专家选择，也可能没人选；
- 对大规模训练不一定方便。

因此现代 MoE 中相对少见。





Global routing via optimization

还有一种方法是把 routing 看作全局优化问题。

比如：

> 给定 token 和 expert 的匹配分数，求一个全局最优 assignment。

这类似线性分配问题。

优点：

- 可以显式控制负载均衡；
- routing 结果可能更全局最优。

缺点：

- 计算复杂；
- 不适合极大规模训练；
- 工程实现困难。

所以大模型里最常见的仍然是简单但有效的 top-k routing。

#### Router的种类

Top k

这个就是最常见的，

![image-20260530111846302](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530111846302.png)

这里的过程是这样的

首先是u，先会经过一个全连接层，变成ue，然后经过softmax，得到s

对于softmax后的，取topk，然后得到g，这里的g就是说给所有专家的权重，刚才取了topk，就会去选择，给这k个ffn加权，没选到的权重自然就是0，然后最后再输出就行了

此外，这里的做法是，先对输入做softmax，然后再输出top k，还有一个做法是先取top k，然后对于每个ffn再做softmax

**先 softmax 再 top-k**

特点：

- 所有专家都参与概率归一化；
- top-k 专家的概率受到未选中专家的影响；
- 早期模型中较常见。

DeepSeek V1/V2、Grok、Qwen 等采用类似做法。

**先 top-k 再 softmax**

特点：

- 只在被选中的专家之间归一化；
- 被选中专家的权重更集中；
- Mixtral、DBRX、DeepSeek V3 等采用类似做法。

这类细节会影响 router 的学习动态和专家权重分布。





![image-20260530112230105](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530112230105.png)

**Fine-grained experts**

DeepSeekMoE 提出了一种 fine-grained expert segmentation 的思路。

普通 MoE 可能是：

```
8 个大专家，每次激活 2 个
```

Fine-grained MoE 可能是：

```
64 个小专家，每次激活 6 个
```

核心思想是：

> 把原本较大的专家拆成更多小专家，使 router 有更细粒度的组合空间。

好处：

- 专家选择更灵活；
- token 可以组合多个细粒度能力；
- 总参数量可以增加；
- activated parameters 仍然可控。

------

**Shared experts**

DeepSeek / Qwen 中还使用了 shared experts。

Shared expert 的特点是：

> 不经过 routing，所有 token 都会使用。

也就是说，模型同时有：

```
Routed experts: token 根据 router 选择其中一部分
Shared experts: 所有 token 都会经过
```

直觉上，shared experts 负责学习通用能力，routed experts 负责学习更专门化的能力。

可以理解为：

```
Shared experts: 公共基础能力
Routed experts: 条件化专门能力
```

------

** DeepSeek 和 OlMoE 的 ablation**

课件中展示了 DeepSeek 和 OlMoE 的消融结果。

DeepSeek 的实验大致表明：

- 更多专家有帮助；
- fine-grained experts 有帮助；
- shared experts 通常有帮助。

但 OlMoE 的结果有一点不同：

- fine-grained experts 有明显收益；
- shared experts 在 OlMoE 设置下没有明显收益。

这个说明：

> MoE 的一些设计不是绝对正确的，需要结合模型规模、训练数据、routing 方式和系统设置一起看。

**Hash routing**

这个一般作为baseline去用吧

![image-20260530112844554](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530112844554.png)



就是过一个hash function，然后选择一个ffn层就行

优点：

- 简单；
- 负载可能比较均匀；
- 不容易出现 router 训练不稳定。

缺点：

- 不会根据语义自适应选择专家；
- 专家分工不一定合理；
- 上限通常不如学习式 routing。



**RL routing**

这里是说，routing用RL来去训练

直觉上，routing 是一个离散动作：

```
state = token hidden state
action = 选择哪个专家
reward = 模型 loss / downstream performance
```

所以用 REINFORCE 之类的方法似乎很自然。

但课件指出，RL routing 虽然可以工作，但没有明显到成为主流。

主要原因：

- gradient variance 高；
- 训练复杂；
- 实现成本高；
- 相比 top-k + auxiliary loss，收益不够大。

所以可以记住：

> RL routing 理论上更“正确”，但实践中不如 heuristic top-k routing 简单稳定。

**Linear assignment routing**

还有一种方法是把 routing 当成 matching / assignment problem。

比如：

```
token-expert score matrix
→ solve assignment
→ 得到 token 到 expert 的分配
```

这可以更强地控制负载均衡，但大规模训练时成本较高，所以不是主流。

## Training objective

MoE 训练的核心难点是：

> 我们希望模型是 sparse 的，因为 sparse 才能省计算；
>  但 sparse gating 是离散选择，不容易用普通反向传播训练。

课件列出三类方案：

1. Reinforcement learning
2. Stochastic perturbations
3. Heuristic balancing losses

实际中最常用的是第三类：**heuristic balancing losses**。

### 

### RL for routing

用 RL 训练 routing 是一个自然想法。

因为 routing 决策可以被看成 action：

```
action = 给 token 选择 expert
```

可以用 REINFORCE 估计梯度。

但是课件总结：

> RL routing 可以工作，但没有好到成为 clear win。

原因是：

- 方差大；
- 实现复杂；
- 训练不稳定；
- 收益不够显著。

所以在现代 LLM MoE 中，RL routing 并不是主流

### Stochastic approximations

另一类方法是在 routing 中加入随机扰动。

**Shazeer et al. 2017 的 noisy top-k**

早期 MoE 使用了 noisy top-k gating。



![image-20260530113752233](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530113752233.png)

形式大致是：

```
G(x) = Softmax(KeepTopK(H(x), k))
```

其中：

```
H(x)_i = x · W_g_i + StandardNormal() · Softplus(x · W_noise_i)
```

也就是说，router score 不是完全确定的，而是加了噪声。

这样做的目的：

1. 促进 exploration；
2. 避免过早固定到某几个专家；
3. 让专家更鲁棒；
4. 让模型学习专家之间的排序关系。

------

**Switch Transformer 的 jitter**

Fedus et al. 2022 中也用过 stochastic jitter。

做法是在训练时对 router 输入或 logits 施加均匀的乘法扰动。

直觉类似：

> 给 routing 加一点噪声，让专家选择不要太脆弱。

但是课件也提到，后续 Zoph et al. 2022 中这个 jitter 被移除过。
 这说明 stochastic routing trick 不一定总是稳定有效。

###  Heuristic balancing losses

这是现代 MoE 最重要的训练技巧。

####  为什么需要 load balancing？

如果没有 load balancing，router 很容易把大量 token 分给少数几个专家。

结果是：

```
Expert 0: 很多 token
Expert 1: 很多 token
Expert 2: 几乎没 token
Expert 3: 几乎没 token
...
```

这会导致几个问题：

1. **计算效率差**
    少数专家过载，拖慢整体 step time。
2. **专家浪费**
    没有 token 的专家学不到东西。
3. **训练不稳定**
    router 可能越来越偏向少数专家。
4. **系统通信不均衡**
    如果热门专家在某些 GPU 上，会导致设备负载不均。

所以 MoE 通常要加 balancing loss。

------

#### Switch Transformer 的 auxiliary loss

Switch Transformer 使用的 load balancing loss 大致形式是：

```
loss = α · N · Σ_i f_i · P_i
```

![image-20260530114003123](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530114003123.png)



其中：

- `N` 是专家数量；
- `f_i` 是实际被分配到 expert i 的 token 比例；
- `P_i` 是 router 分配给 expert i 的平均概率；
- `α` 是 loss 权重。

直觉是：

> 如果某个专家实际接收 token 很多，同时 router 也给它很高概率，那么这个 loss 会变大。

这个 loss 会推动 router 更均匀地使用专家。

------

 **这个 loss 的直觉**

可以用一个简单例子理解。

假设有 4 个专家，理想情况下每个专家接收 25% token。

如果现在：

```
Expert 0: 70%
Expert 1: 20%
Expert 2: 5%
Expert 3: 5%
```

那么 Expert 0 明显过载。
 load balancing loss 会惩罚这种分布，让 router 后续降低 Expert 0 的选择概率。

所以它本质上是：

> 给热门专家降温，给冷门专家机会。



### DeepSeek V1/V2 的 balancing

DeepSeek V1/V2 使用了几种 balancing 机制。

#### Per-expert balancing

这和 Switch Transformer 类似，目标是让不同专家接收 token 的比例更均衡。

形式上，它会计算每个专家的：

- 实际 token 使用比例；
- router 分配概率；

然后构造辅助 loss。

![image-20260530114257862](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530114257862.png)



------

####  Per-device balancing

在大规模训练中，专家会分布在不同设备上。

如果 expert-level balance 做得还可以，但设备层面不均衡，也会有问题。

比如：

```
GPU 0 上的专家整体很忙
GPU 1 上的专家整体很闲
```

这会导致：

- GPU 0 成为瓶颈；
- 整体训练速度下降；
- all-to-all 通信不均衡。

所以 DeepSeek 还做了 device-level balancing，把同一设备上的专家聚合起来做负载均衡。

![image-20260530114316540](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530114316540.png)



------

####  Communication balancing

DeepSeek V2 进一步考虑通信平衡。

因为 MoE 不只是专家计算，还有 token 在设备间的发送和接收。

通信不均衡会导致：

- 某些设备发送特别多；
- 某些设备接收特别多；
- 网络通信成为瓶颈。

所以 V2 里加入了 communication balancing loss，同时平衡 communication in 和 communication out。

这说明现代 MoE 训练已经不只是算法问题，而是强烈依赖系统设计。

### DeepSeek V3 的 auxiliary-loss-free balancing

DeepSeek V3 提出了一个新的机制：**per-expert bias**。

![image-20260530114510361](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530114510361.png)



####  基本想法

给每个专家设置一个 bias：

```
score_i = original_score_i + bias_i
```

如果某个专家最近用得太少，就提高它的 bias；
 如果某个专家用得太多，就降低它的 bias。

这是一种在线更新机制，用来动态调节专家负载。

直觉上类似：

```
热门专家 → 降低 bias → 之后少选一点
冷门专家 → 提高 bias → 之后多选一点
```

DeepSeek 称之为 **auxiliary-loss-free balancing**。

------



####  但它不完全是 auxiliary-loss-free

课件中特别提醒：

> 这个方法并不是完全没有辅助 loss。

DeepSeek V3 仍然使用了 sequence-wise auxiliary loss，用来避免单个序列内部专家使用极端不均衡。

所以更准确地说：

> DeepSeek V3 减少了传统 load balancing loss 对主训练目标的干扰，但仍然保留了一些辅助平衡机制。

课件展示了一个很重要的现象：

> 没有 load balancing，专家使用会非常不均衡。

表现包括：

- 某些专家被大量使用；
- 其他专家几乎不用；
- loss 曲线可能变差；
- validation loss 变差；
- 训练不稳定。

有 load balancing 时，专家 token 分配会明显更均匀。

所以 MoE 训练中，load balancing 不是可有可无的小技巧，而是非常关键的稳定性机制。

## MoE 的复杂性：all-to-all communication

MoE 的 forward 过程大致是：

```
1. 每个设备上有一批 token
2. router 决定每个 token 去哪些专家
3. token 被发送到专家所在设备
4. 专家计算 FFN
5. 输出被送回原设备
6. 合并专家输出
```

这中间会产生大量 all-to-all communication。

如果通信开销过大，MoE 的理论计算优势就会被吃掉。

所以 MoE 的实际效率高度依赖：

- 专家放置策略；
- token dispatch 实现；
- all-to-all 通信效率；
- 负载均衡；
- sparse matrix multiplication 实现。

------

### Sparse matrix multiplication

Dense FFN 中，所有 token 都经过同一个矩阵乘法：

```
X @ W
```

MoE 中，不同 token 去不同专家，因此变成了很多不规则的小矩阵乘法。

直接实现会很低效。

现代 MoE 系统使用更高级的 sparse matrix multiplication。
 课件中提到 MegaBlocks，它通过 block-sparse matmul 等方式提高 MoE 计算效率。

核心思想是：

> 把不同专家的 token 组织成更适合 GPU 计算的块状矩阵运算。

所以 MoE 的高效实现依赖专门的 kernel 和通信优化。

## 18. MoE 的随机性问题

课件中有一个有趣的小节：MoE 可能带来额外随机性。

### 18.1 为什么 MoE 可能更随机？

MoE 中可能存在 token dropping。

如果某个专家容量有限，而太多 token 被 router 分到这个专家，那么部分 token 可能被 drop 或使用 fallback 策略。

关键在于：

> token dropping 可能发生在 batch level。

这意味着你的 token 是否被 drop，可能受同一个 batch 里其他 token 的影响。

在在线服务中，如果 batch 里混合了不同用户的请求，那么：

```
其他用户的 query
→ 影响 batch 内专家负载
→ 影响你的 token 是否被 drop
→ 影响你的输出
```

这会带来额外非确定性。

课件提到，有人曾猜测 GPT-4 的随机性可能与 MoE 有关。
 不过这只是 speculation，不能当作确定结论。

![image-20260530115137187](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530115137187.png)

## 19. MoE 的稳定性问题

### 19.1 Router 数值不稳定

MoE 中 router 通常会计算 softmax。

如果 logits 数值太大，softmax 会非常尖锐：

```
一个专家概率接近 1
其他专家概率接近 0
```

这可能导致：

- routing 过早塌缩；
- 专家分布不均；
- 梯度不稳定；
- loss spike。

尤其是在低精度训练中，比如 bf16 / fp16，router logits 的数值误差会被放大。

![image-20260530115323318](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530115323318.png)





------

### 19.2 解决办法：router 用 float32

课件给出的一个重要建议是：

> router 使用 float32。

即使模型主体用 bf16 训练，router 部分也可以保留 fp32 来提高稳定性。

这在 MoE 中非常常见，因为 router 虽然参数量很小，但对训练影响很大。

------

### 19.3 Router z-loss

另一个技巧是 router z-loss。

z-loss 的作用是约束 router logits 的规模，避免 logits 爆炸。

大致形式是：

```latex
L_z = (1 / B) Σ_i (log Σ_j exp(x_j^i))^2
```

直觉是：

> 惩罚过大的 logsumexp，让 router logits 不要无限变大。

课件中展示了去掉 z-loss 后训练曲线可能变得不稳定，出现 loss spike 或 benchmark 波动。

可以记住：

> z-loss 是 MoE router 稳定性的关键技巧之一。

## 20. MoE 的 fine-tuning 问题

课件指出，Sparse MoE 在小数据微调时可能更容易过拟合。

### 20.1 为什么 MoE fine-tuning 更容易过拟合？

原因包括：

1. **稀疏激活**
    每个样本只更新部分专家。
2. **专家数据量不均**
    某些专家可能在微调数据中被频繁更新，其他专家几乎不更新。
3. **小数据分布窄**
    router 可能把特定任务数据集中送到少数专家，导致专家过拟合。
4. **参数总量大**
    MoE 总参数量大，在小数据上更容易记忆训练集。

------

### 20.2 Zoph et al. 的方案

Zoph 等工作中的一种方案是：

> fine-tune non-MoE MLPs，而不是更新所有 MoE 专家。

也就是说，微调时不要完全打开所有专家参数，而是只调部分模块，从而减少过拟合。

![image-20260530115545976](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530115545976.png)

------

### 20.3 DeepSeek 的方案

DeepSeek 的方案比较直接：

> 使用大量 SFT 数据。

课件提到 DeepSeek 使用了约 1.4M SFT 数据。

这说明 MoE fine-tuning 如果要做得稳，最好有足够大的指令数据覆盖面。

![image-20260530115555891](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530115555891.png)

## 21. Upcycling：用 Dense LM 初始化 MoE

接下来课件讲了另一种训练方式：**upcycling**。

### 21.1 什么是 upcycling？

Upcycling 指的是：

> 不从零开始训练 MoE，而是用一个已经训练好的 dense model 初始化 MoE。

做法大致是：

```
原始 dense FFN
→ 复制成多个 experts
→ 加入 router
→ 继续预训练
```

比如原来有一个 dense FFN：

```
FFN
```

可以复制成：

```
Expert 1 = copy of FFN
Expert 2 = copy of FFN
Expert 3 = copy of FFN
...
```

然后训练 router 和 experts。

------

### 21.2 Upcycling 的好处

相比从零训练 MoE，upcycling 有几个优势：

1. **利用已有 dense 模型能力**
    不需要从随机初始化开始学语言能力。
2. **训练成本更低**
    可以在已有模型基础上继续训练。
3. **更容易得到可用模型**
    初始模型已经有不错能力，MoE 化后继续提升。
4. **适合已有 dense checkpoint 的团队**
    如果已经有 dense base model，可以尝试扩展成 MoE。

## 22. Upcycling example：MiniCPM

课件介绍了 MiniCPM-MoE。

特点：

## 25. DeepSeek MoE V1

DeepSeek MoE V1 的配置：

```
Total parameters: 16B
Activated parameters: 2.8B
```

主要设计：

1. Standard top-k routing
2. Shared experts
3. Fine-grained experts
4. Standard auxiliary load balancing
5. Expert-level balancing
6. Device-level balancing

DeepSeek V1 使用：

```
Shared experts: 2
Fine-grained routed experts: 64
Active routed experts: 6
```

它的核心贡献在于把 shared experts 和 fine-grained experts 结合起来。

可以理解为：

```
通用能力 → shared experts
专门能力 → routed fine-grained experts
```

------

## 26. DeepSeek MoE V2

DeepSeek V2 规模更大：

```
Total parameters: 236B
Activated parameters: 21B
```

主要变化：

1. 更多专家；
2. 更大的 activated parameters；
3. top-M device routing；
4. communication balancing loss；
5. 更强系统优化。

配置大致是：

```
Shared experts: 2
Fine-grained routed experts: 160
Active experts: 6
```

### 26.1 Top-M device routing

因为专家分布在多个设备上，如果一个 token 的 top-k experts 分散在太多设备，会导致通信成本变高。

Top-M device routing 的想法是：

> 限制 token 只路由到若干个设备上的专家，从而降低通信开销。

这体现了 MoE 中模型结构和系统效率之间的强耦合。

------

### 26.2 Communication balancing

V2 加入 communication balancing loss，目标是平衡设备之间的通信量。

它不只是看专家计算负载，还看：

- 哪些设备发送 token 多；
- 哪些设备接收 token 多；
- 通信是否成为瓶颈。

这说明大规模 MoE 的优化目标已经包括：

```
模型效果 + 训练稳定性 + 设备负载 + 通信效率
```

------

## 27. DeepSeek MoE V3

DeepSeek V3 进一步扩大规模：

```
Total parameters: 671B
Activated parameters: 37B
```

主要配置：

```
Shared experts: 1
Fine-grained routed experts: 256 / 258 级别
Active experts: 8
```

课件中提到的新东西包括：

1. Sigmoid + softmax top-k
2. top-M device routing
3. auxiliary-loss-free balancing
4. sequence-wise auxiliary loss
5. per-expert bias

------

### 27.1 Sigmoid + Softmax top-k

DeepSeek V3 的 routing 不再只是简单 softmax。

大致流程可以理解为：

```
router score
→ sigmoid
→ top-k selection
→ selected experts 内部重新归一化
```

这种设计可能让专家选择更灵活，并改善 router 的数值行为。

------

### 27.2 Aux-loss-free balancing

DeepSeek V3 使用 per-expert bias 来动态调节专家负载。

如果某专家使用不足：

```
bias ↑
```

如果某专家过载：

```
bias ↓
```

这样可以减少传统 auxiliary balancing loss 对主语言模型 loss 的干扰。

不过课件也指出，它仍然有 sequence-wise auxiliary loss，所以不是完全没有辅助约束。

## 29. MLA：Multi-head Latent Attention

### 29.1 MLA 的基本想法

MLA 的核心思想是：

> 把 Q、K、V 表示为低维 latent activation 的函数。

普通 attention 中，推理时需要缓存每个 token 的 K/V：

```
KV cache = K, V for every previous token
```

长上下文时，KV cache 会非常占显存。

MLA 试图压缩这个 cache：

```
hidden state
→ lower-dimensional latent
→ reconstruct K/V when needed
```

这样推理时只需要缓存较小的 latent representation。

![image-20260530120429115](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530120429115.png)



------

### 29.2 MLA 的好处

主要好处是降低 KV cache 成本。

在长上下文推理中，KV cache 可能是主要显存瓶颈。
 MLA 通过低维 latent 表示减少缓存体积。

课件中还提到，某些矩阵可以合并到 Q projection 中，从而进一步优化计算。

------

### 29.3 MLA 的复杂点：RoPE 冲突

RoPE 是现代 LLM 常用的位置编码方式。

但 MLA-style caching 和 RoPE 有冲突，因为 RoPE 需要对 Q/K 做旋转，而 MLA 希望压缩和重构 K/V。

课件中提到 DeepSeek 的解决方法是：

> 保留一部分 non-latent key dimensions，让这些维度可以正常做 RoPE rotation。

也就是说，不是所有 key 都被 latent 压缩，有一部分显式 key 维度专门用于位置编码。

![image-20260530120515521](https://cdn.jsdelivr.net/gh/ShiangHou/markdown_image/img/image-20260530120515521.png)





------

## 30. MTP：Multi-token Prediction

MTP 指的是让模型预测多个未来 token。

普通语言模型训练目标是：

```
predict next token
```

MTP 则希望模型同时学习预测多个未来 token：

```
predict token t+1
predict token t+2
predict token t+3
...
```

课件里提到 DeepSeek V3 使用了 MTP，但实际上只做了 one-token ahead 的版本。

MTP 的潜在好处包括：

- 提升表示学习；
- 让模型学习更长跨度的预测结构；
- 可能辅助 speculative decoding / draft model 相关能力。

不过这一部分课件没有展开太多，主要是作为 DeepSeek V3 的补充技术出现。

## 31. 本章总结

课件最后总结了 MoE 的核心观点。

### 31.1 MoE 利用稀疏性

MoE 的本质是：

```
不是所有输入都需要完整模型
```

通过 sparse activation，每个 token 只使用一部分专家。

这使得模型可以拥有很大的总参数量，同时保持每个 token 的计算量相对可控。

------

### 31.2 Discrete routing 很难，但 top-k 很有效

严格来说，routing 是离散不可微的选择问题。

理论上可以用 RL 或全局优化解决，但实践中最常用的是：

```
top-k routing + auxiliary balancing loss
```

虽然这是 heuristic，但它在大量现代 MoE 模型中都表现很好。

------

### 31.3 现在有大量经验证据说明 MoE 有效

从 Switch Transformer、GShard，到 Mixtral、DeepSeek、Qwen、OlMoE，越来越多结果表明：

> MoE 是一种有效且 cost-effective 的大模型扩展方式。

它尤其适合：

- 想增加总参数量；
- 但又不希望每个 token FLOPs 线性增加；
- 并且有足够多设备支持 expert parallelism 的场景。

------

## 32. 这章最应该记住的几个点

### 32.1 MoE 的一句话理解

> MoE 是把 Transformer 的 FFN 换成多个专家，并用 router 让每个 token 只激活少数专家，从而在相似计算量下扩大模型容量。

------

### 32.2 MoE 的核心收益

```
更多总参数
更少激活参数
相对可控的 FLOPs
更好的 compute efficiency
更适合多机多卡扩展
```

------

### 32.3 MoE 的核心难点

```
routing 不可微
专家负载不均
训练不稳定
router 数值敏感
系统通信复杂
fine-tuning 容易过拟合
```

------

### 32.4 现代 MoE 的典型 recipe

一个现代 MoE 大模型通常会包含：

```
1. MLP MoE layer
2. token-choice top-k routing
3. fine-grained experts
4. shared experts
5. load balancing loss 或 per-expert bias
6. router fp32
7. router z-loss
8. expert parallelism
9. sparse matmul 优化
10. 大规模 SFT / carefully designed fine-tuning
```

------

### 32.5 MoE 不是单纯的模型结构问题

MoE 同时涉及：

```
模型结构
训练目标
数值稳定性
分布式训练
通信优化
推理服务
fine-tuning 策略
```

所以它是一个典型的 **algorithm-system co-design** 问题。

------

## 33. 对这章的个人理解版总结

如果用更直观的话总结：

Dense 模型像是一个“所有问题都找同一个大团队解决”的系统。
 MoE 模型像是一个“有很多专家部门，根据问题类型分配给不同专家处理”的系统。

它的好处是：

- 专家多，总能力强；
- 每次只找少数专家，成本低；
- 不同专家可以学不同能力。

但难点是：

- 怎么分配任务；
- 怎么避免某些专家太忙；
- 怎么避免某些专家没活干；
- 怎么让跨设备通信别拖慢训练；
- 怎么让 router 稳定训练。

所以 MoE 的核心不是“有很多专家”这么简单，而是：

> 如何让专家选择、专家负载、训练稳定性和系统效率同时成立。
